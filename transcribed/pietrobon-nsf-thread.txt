 From the CMOS Processor paper here are the list of instructions for the FDS computer. Cycle time is 2.48 s (403.2 kHz). I was able to obtain some of the opcodes from YouTube video dF_9YcehCZo. I believe the JMP and JMS opcodes are the same, the different names being used to distinguish a normal jump and when jumping to a subroutine. The JMP instruction first saves the 12-bit program counter plus 1 to hardware register B and then directly jumps to the 12-bit operand address. For a subroutine, the SRB instruction saves B to the 12-bit operand address. To return, jump to where the return address is stored. As the 4-bit opcode for a JMP is 0, this causes a jump to the return location. This is a classic example of self modifying code! The FDS has two banks of 4Kx16 memory. Two additional 1-bit registers are used to select between the banks, changed using an OUT instruction. One bit is used for programs and one bit for data. I suspect the operation is similar to the DEC PDP-8. The instruction bit is only selected after a JMP or JMS, to prevent wild program execution. The other bit could be used for selecting data for MRD and MLD instructions. The MRD and MLD transfer data between main memory and one of the 128 registers, located from address 3968 to 4095 in decimal (0F80 to 0FFF in hexdecimal). I suspect five bits of the operand select one of the 31 memory pointers, which contains the address to main memory. The other seven bits could be for one of the 128 registers. I'm not exactly sure how the AMR and AML instructions work, as only the feasibility design were given more description and these instructions weren't included. I suspect though that they increment the memory pointer after the instruction has been performed. The 74 counter registers are probably used by the ISP, DSP, ISZ and DSZ instructions. The ABS instruction is a bit a head scratcher. The paper says it stores the given 12 bit number, but to where? For the seven shift and five arithmetic instructions, the opcode could be ?XYZ, where ? is the unknown code, X indicates which of the instructions is chosen and Y and Z are the address for the 16 general registers located in memory. For SUB, the operation could be R(X) := R(X)-R(Y), where R(x) is the general register given by address x. The other arithmetic instructions are probably similar. The shift instructions could be R(X) := shift(R(Y)). I believe the three hardware registers (A, B and C) are used to temporarily store R(X), R(Y) and the result. I don't know how many bits get shifted for a short or long shift, but the feasibility design had a choice of 2, 4, 8 or 16 bits. The seven index registers (again in memory) is only used by the OUT instruction. Three bits of the operand would select the index register. If the selected index register is zero, then data is output according to the remaining nine bits of the operand. This simplifies the timing for sending out data. Only one instruction directly modifies an index register, MCX. The operand could be three bits for the index register and seven bits for one of the 128 registers in memory, which stores the initial value. The feasibility design had other instructions to increment, decrement or set an index register. An 2.5 ms interrupt was added that goes to address zero. This is used to check the various counters to ensure the software is not accidentally running data. The CPU itself only uses 1/3 W of power! The FDS hardware was designed so that one bit in one of the State Vector Control words may be set to allow the DTR Direct Memory Access (DMA) channel to run at one half the DTR bit rate. The DMA provides sequential data words from selected buffers in FDS memory to the DTR input buffer at one half the bit rate of the DTR. This results in each bit of data being recorded as two sequential, identical bits. The DMA interrogates the DTR output buffer at one half the playback bit rate and loads the resultant data stream into sequential addresses in the FDS memory. The data to FDS memory is thus every other bit of the data from the DTR. This combination of recording and playback allows the minimum DTR record rate of 7.2 kb/s to be circumvented. A 3.6 kb/s data stream is doubly recorded to provide the DTR minimum of 7.2 kb/s, then on playback only every other bit of the DTR 7.2 kb/s readout is processed through the DMA channel; thus, recovering the original 3.6 kb/s data stream.  I hope the following helps those who might be confused by all the document references being thrown around: NASA Dr. James Tomayko was a professor at Wichita State University (WSU) at the time he wrote a report for NASA, Computers in Spaceflight (PDF), 1988. The archived HTML version of the Voyager chapter/section in the report: history.nasa.gov/computers/Ch6-2.html and the source footnotes for the Voyager chapter/section: history.nasa.gov/computers/Source6.html (It may not look it, but the HTML version of the report is a very accurate rendition of the report's text and includes all the illustrations from the report. I think I only noticed one typo in the Voyager chapter and I've studied the HTML and scanned PDF versions many times.) Wichita State University The WSU collection linked to by Steven (and from which he got the FDS design paper) presumably includes copies of all the items in the source footnotes above, many of which are internal JPL documents (JPL obviously has the originals): Dr. James E. Tomayko Collection of NASA Documents Incidentally, Dr. Tomayko was a historian of technology who passed away in 2006. He was very active in computer history and computer education circles. YouTube The YouTube video that Steven and I reference: Bruce Waggoner, Voyager Mission Assurance Manager, (August 2024) Waggoner mentions that he had to get permission to show the FDS code fragment in his presentation. Quote from: leovinus on 11/13/2024 01:43 pm Even better, without even posting such a document, someone could build a derived work such as an assembler/disassembler piece of code to document the FDS instructions for the future. Happy to help That actually might be of help to JPL! (Especially considering JPL has had to lay off an eighth of its workforce in 2024 per Ars Technica . ) Waggoner said in his presentation (and JPL has said elsewhere) that they don't have an assembler and that translation of the memory anomaly fixes to machine code was done by hand. If they don't have an assembler, I doubt they have a disassembler. And Waggoner also said that they didn't have an up-to-date listing of the code running on the FDS computer and worked from a listing in an old Microsoft Word document. Other sources say that full memory readouts from the Voyagers' computers are done on a regular basis, so a disassembler would have definitely helped.
