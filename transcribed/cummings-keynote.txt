The Anomaly

 • On Nov. 14, 2023, VGR-1 stopped sending meaningful data
 • We were receiving a signal, but it was a string of all 1’s or all 0’s
 • By the time I joined the team (about a week later), the team had already concluded that the
   FDS (Flight Data Subsystem) was the most likely cause
 • The FDS is one of 3 subsystems with processors and associated flight software. Also:
     • CCS (Computer Command Subsystem)
     • AACS (Attitude and Articulation Control Subsystem)

How We Diagnosed It
Focus on FDS flight software


    • By early January, we were looking more closely at the FDS flight software
    • It was seeming increasingly likely that either
          • The FDS FSW had failed in some way due to a processor error, or
          • The FDS processor was sound, but the FSW had failed in some way due to a memory error
    • Swapping to the backup FDS processor was possible, but
          • It was deemed risky
          • We felt a memory error was more likely

How We Diagnosed It
FDS FSW Structure


   • Every 2.5 ms an interrupt fires that restarts FSW execution at location zero
   • Therefore, FSW is broken up into 24 sequential chunks of execution called “P periods”, 2.5
     ms each
   • There is a jump table (“P Table”) with pointers to the code for each P period (pointers to the
     24 “P routines”)
   • There is a counter (“P counter”) that keeps track of the next P routine to execute
   • One complete cycle through the 24 P routines takes 24 x 2.5 ms = 60 ms (a “line”)
   • 800 lines is called a “frame”, and it requires 800 x 60 ms = 48 seconds




                       "This document has been reviewed and determined not to contain export controlled CUI."
How We Diagnosed It
P Tables and data mode

   • There are 10 different “data modes” that the spacecraft can execute
         • Each data mode can be thought of as a different program to execute
   • Which data mode the spacecraft is currently executing is determined by a ground command
   • In order to support these 10 different data modes, there are 4 P Tables
         • First P Table supports GS-4B, GS-8, PB-5, PB-14, PB-15
         • Second P Table supports just EH-12
         • Third P Table supports just EL-40
         • Fourth P Table supports UV-5A, PB-16, CR-5T

How We Diagnosed It
Second of two parallel activities to pursue FDS memory corruption hypothesis


    • Command the spacecraft to execute each of the 10 data modes
          • Force the FSW to break out of its hypothesized “stuck” state and do something, anything
              • “Anything” because some of the data modes transmit data at rates too high to be received
    • Unfortunately, there is a lot of shared code
          • Subroutines called by all P Tables
          • One P routine sometimes jumps into a different P routine
              • Sometimes across P Tables
    • Therefore, the hypothesized bit flip could cause more than one P Table to get “stuck”
          • Still, we thought it was worth a try

The Fix
      "This document has been reviewed and determined not to contain export controlled CUI."
Fix overview

 • Find a 256-word section of memory that is available
 • Relocate the 256 instructions from the corrupted addresses (0x1400 - 0x14FF) to the available
   memory
 • Identify all places in the rest of the code that reference the code being relocated
     • Calls, jumps, or data accesses
 • Fix up those references to refer to the new (relocated) addresses
 • Use upper memory (upper 4K words) for relocation
     • Reduces risk
         • Calls/jumps/accesses between upper memory and lower memory add complexity
         • Also affects execution timing

Challenges

 • JPL designed processor with custom instruction set
    • A document that may or may not be accurate
 • No source code files
    • Source code listing in Microsoft Word with errors
    • May or may not match the version on the spacecraft
 • No assembler
 • No simulator
 • No testbed
 • Telemetry must be restored as soon as possible!!!
    • No visibility into an aging and delicate spacecraft

 • AND: We were unable to find 256 contiguous words of memory that were unused!

Addressing those challenges

 • Do it in 2 phases
     • Phase 1, Engineering Telemetry Mode: EL-40
     • Phase 2, Science Telemetry Modes: GS-4B, PB-14, CR-5T
 • Sacrifice EH-12 code - High-Rate (1200 bps) Engineering-Only data mode
     • Gave us the required 256 available words in upper memory
     • BUT not contiguous, due to sharing of code between EH-12 and other data modes
 • Modify binary instructions
     • Too time-consuming to develop and certify assembler
 • Test by inspection
     • Too time-consuming to develop and certify simulator
     • Enlisted help from Matt Wette and Armen Arslanian
     • Over time, created an extensive checklist, and iterated over it repeatedly
     • Accepted that we will never achieve 100% confidence

Patch 1: Relocate corrupted code reference by EL-40


    • Find contiguous subsets of EH-12 code that are available as relocation destinations
          • Must not be used (shared) by any other data mode
          • Required tracing backwards through all call trees
          • Reliance on inspection to accurately identify shared code was error-prone
              • We knew there were errors in the source code listing
              • Therefore, could not rely solely on labels to identify sharing

          • If we overlooked some sharing, then relocation to that area would break other data modes
    • Identify corrupted subroutines that are referenced by EL-40
          • Required similar back-tracing through code
          • If we overlooked some EL-40 references, EL-40 could fail unpredictably

Phase 1: Engineering Telemetry Patch
Patch 2: Fix up all EL-40 references to corrupted code

    • Modify each EL-40 reference that was found so it refers to new address of relocated
      subroutine or data
    • Special case: Calls to COPY subroutine, which was in corrupted memory
          • Copies memory contents from memory A to memory B
          • Unneeded, because Voyager 1’s FDS memory B deemed unusable since 1981
          • Therefore, NO-OP the COPY subroutine instead of relocating it
              • Replace “JMP COPY” with “WAT 344” to preserve timing
          • BUT, calls to COPY have a side effect
              • COPY subroutine sets the processor to lower address mode
              • Leaves it in that mode when it exits
              • Analyzed all callers of COPY, and determined that none relied on this side effect
              • Therefore, safe to just NO-OP each call

 • Patch 1 and Patch 2 each consisted of a set of <address, value> pairs to be uplinked
 • Our checklist covered all of the potential pitfalls discussed above for developing Patch 1 and

     • Addresses that one section of code is relocated to must not conflict with addresses that other

     • Relocated addresses for each subroutine or piece thereof are consecutive
